## Why this exists

The 2026-09-03 audit's clean list noted that the 128 magic constants in
`src/bb_tables.hpp` were produced in this repository by commit `a5dbe68`
("Generatd magic numbers", 2023-03-28) with a xorshift generator seeded
`1804289383` -- the seed the "Bitboard chess engine in C" series uses -- so they
coincide, value for value, with that series' published set. The code was the
owner's and the origin is in git, which is why this is not a COPYING violation
and not an audit finding; it is a coincidence with a published table sitting in
the tree with no note, and the generator that produced it did not survive into
this branch.

DEC-132 is the owner's decision of 2026-09-04: keep the constants for now, cite
the entry at the table, and let this step end the coincidence by making the
provenance a command -- a committed generator and a seed this project chose --
rather than an argument.

## Cost

Small and machine-light. The generator is about 130 lines in `a5dbe68`, to be
rewritten against the current types. Regenerating is seconds. The proof is the
perft verification `bench_movegen` already performs, `test_perft`, and the two
`search_bench` node-count runs, none of which need a match: a magic number is a
perfect hash of the relevant occupancies into a table whose size is fixed by
the relevant-bit count, so a different valid set changes which slot each
occupancy lands in and nothing the move generator returns.

## Amended 2026-09-05: the Zobrist keys too

`2026-09-04_test_review-F08` found the keys drawn through
`std::uniform_int_distribution<uint64_t>` over `mt19937_64`
(`src/bitboard.cpp`, `init_zobrist`). The distribution's output is
implementation-defined, so keys, table indices and node counts may differ
between standard libraries; they matched between glibc and Apple libc++ when
the MacBook handover check ran, which is a measurement and not a guarantee.
The owner folded the fix in here (DEC-139): the generator this step commits
produces the keys under the project seed as well, so both tables that must be
this project's own output come from one command. Unlike the magics, new keys
change the table indices and therefore the node counts, once; the accepts
says how that is recorded.
