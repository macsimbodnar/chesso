# Code comments in agent rule files: vendor guidance, real AGENTS.md and CLAUDE.md files, and what is measured

Read 2026-11-01. Evidence labels: **[V]** vendor instruction in official docs. **[P1]** agent prompt read from the vendor's own open-source repo. **[P2]** prompt from a third-party extraction or leak, provenance unverified. **[R]** rule text in a real repository, read from the file through the GitHub API on 2026-11-01. **[O]** practitioner opinion. **[M]** measurement. Quotes are exact unless marked as a summary. WebFetch's summariser returned the Copilot, Cursor, Aider, Windsurf, Factory, Jules, agents.md, Codex-docs and umans pages, so those quotes are short and I did not see the raw page. Anthropic docs, GitHub files and arXiv HTML were read raw.

## What do official docs say about comments?

### Takeaway
Almost none of the official documentation pages read gives a code-comment policy. The real vendor comment rules live in system prompts (next section). Docs give only general rule-writing advice: short, specific, checkable, and a hook for what must always hold. The one general docs-level comment rule found (Gemini CLI's sample) points the opposite way from the prompts: it requires doc comments. Length guidance ranges from 200-400 words (Codex `/init`) to an 80,000-character cap (Factory), and precedence models conflict.

#### Contradictions between vendors
- **Should an agent write comments by default?** Gemini's docs sample demands JSDoc on all new functions and classes. Claude Code's and Codex's prompts default to none (next section). Copilot, Cursor, Aider, Windsurf and Factory docs do not say.
- **Length.** Anthropic under 200 lines. Cursor under 500 lines. Codex `/init` 200 to 400 words, while Codex accepts 32 KiB. Copilot template 2 pages. Factory caps at 80,000 characters. agents.md gives no limit. Sources as above.
- **Conflicts.** agents.md: closest file "wins". Codex: later text overrides. Claude Code: additive, Claude "may pick one arbitrarily". A nested override that works on Codex is not promised on Claude Code.
- **Top of file.** Factory says to keep the top dense, and GitHub says early. Codex says later text overrides. These are different questions (salience versus conflict), and the docs do not reconcile them.

### Inferences
- A comment rule cannot rely on a vendor doc. It has to be written from the prompt-level defaults, which it will extend or fight.
- "Longer files reduce adherence" is a vendor assertion with no cited data. See the measurement section.
- In a repo with a root `CLAUDE.md`, a nested `src/AGENTS.md` looks unread by Claude Code unless imported. Path-scoped rules or a nested `CLAUDE.md` with an import are the working forms. This is my reading of the docs and I did not test it.

## What do published or leaked agent system prompts instruct about comments?

### Takeaway
Nearly all prompts converge on "few comments, explain why, never talk to the reader through them". OpenAI's prompts split: base and GPT-5.x say no inline comments unless requested, while the Codex-model prompts allow rare comments that explain *what* is going on. Claude Code softened from an all-caps ban to "default to no comments, why only". Default agent behaviour therefore already leans against comments, and a rule asking for more or longer comments runs against the prior.

### Cited Findings

#### Claude Code ([P2], extracted from the npm bundle by Piebald, not published by Anthropic)
Piebald states the strings are "extracted directly from Claude Code's compiled source code" and tracks v2.1.316 of 30 Oct 2026. - "Don't explain WHAT the code does, since well-named identifiers already do that. #### Contradictions inside and between prompts
- **OpenAI against itself:** "Do not add inline comments ... unless explicitly requested" versus "Add succinct code comments that explain what is going on". The rule changes with the model chosen.
- **What versus why:** Codex-model prompts say explain "what is going on". Claude Code says "Don't explain WHAT". Early Gemini CLI and Cursor say why. A repo rule that only says "why, not what" repeats some defaults and contradicts others.
- **Direction:** Kiro says include comments. Gemini's docs sample requires JSDoc. Claude Code, Codex base, Amp and Devin default to none.

### Inferences
- Under Claude Code and Codex a rule requiring a comment is an against-prior rule, which is the class Harness-IF measures as least followed (see compliance section). A rule that only says "few comments, why not what" adds little on those agents.
- Claude Code's text bans comments that say "where it came from". A repo whose comments deliberately cite a step id, decision id or measurement is in direct conflict with that text and must say so explicitly.
- Prompts change between versions without notice in the repo using them, so a repo rule should state its own policy and not lean on the default.

### Gaps
- No vendor has published Claude Code's prompt, so its text stays [P2].
- The Codex-model prompt files last changed on 12 Jan 2026. Whether current Codex builds still select them for any model is unverified.
- `opencode` and `cline` prompt paths I tried returned nothing and are not reported. No Jules, Copilot-cloud-agent or Antigravity comment text was verified.
- No vendor explains why its comment rule is worded as it is, and no vendor has published comment-rule eval data.

## What do AGENTS.md and CLAUDE.md files in well-known repositories actually say about comments?

### Takeaway
In a non-random sample of 43 well-known repos I read, 21 have an explicit policy on code-comment content, and most say "why, not what". Newer files go further: no session or change history in comments, write for a reader without the PR, preserve existing comments. The strongest designs make the rule checkable: telegramdesktop rations comment lines with a `// WHY:` marker and hooks, and PostHog tags each rule with what enforces it. Ruff is the clear case of allowing more length. No top-tier repo tells agents to write long comments as a default. Rule placement varies from line 4 to line 414, so there is no convention.

- Biome: "Write for a contributor reading the code at HEAD without access to the conversation, issue, PR, or diff." "Delete comments that only restate names, types, or control flow." — [biome AGENTS.md](https://github.com/biomejs/biome/blob/HEAD/AGENTS.md)
- PostHog: "**Never log change history or chat context in code.** `[review]` No \"previously did X, now does Y\", no \"per <task/PR>\", no \"changed because…\", no \"AI:\" or \"agent:\" notes." — [posthog AGENTS.md](https://github.com/PostHog/posthog/blob/HEAD/AGENTS.md)
- Coder: "Comments must be concise and substantive. Explain behavior, constraints, or rationale, not the history of the edit." — [coder AGENTS.md](https://github.com/coder/coder/blob/HEAD/AGENTS.md)

#### Preserving existing comments ([R])
- Elasticsearch: "Do not remove existing comments from code unless the code is also being removed or the comment has become incorrect." — [elasticsearch AGENTS.md](https://github.com/elastic/elasticsearch/blob/HEAD/AGENTS.md)
- Ruff: "Preserve useful human-written comments unless the code change makes them inaccurate." — [ruff AGENTS.md](https://github.com/astral-sh/ruff/blob/HEAD/AGENTS.md)
- PostHog: "**When refactoring or moving code, keep the existing comments** unless the change actually makes them obsolete." — [posthog AGENTS.md](https://github.com/PostHog/posthog/blob/HEAD/AGENTS.md)
- telegramdesktop: "Do not remove existing comments just to satisfy this rule." — [tdesktop AGENTS.md](https://github.com/telegramdesktop/tdesktop/blob/HEAD/AGENTS.md)

#### Repos that allow or want long comments ([R])
- **Ruff, the clearest case** (line 234 of 239): "Don't use comments to narrate code, but do use them to explain invariants and why something unusual was done a particular way. Make sure that a comment will make sense to somebody who's reading the code for the first time. Prefer plain language, avoid jargon, and don't be afraid to be more verbose if it's necessary to explain something well. Giving examples of the kind of Python code we're trying to model at this particular point in Ruff or ty can often be very helpful for future readers of the code." — [ruff AGENTS.md](https://github.com/astral-sh/ruff/blob/HEAD/AGENTS.md)
- **Elasticsearch**: requires Javadoc for new public API, "explaining the \"why\" rather than the implementation details" — [elasticsearch AGENTS.md](https://github.com/elastic/elasticsearch/blob/HEAD/AGENTS.md)
- **TigerBeetle's style guide** (human style doc, no root AGENTS.md or CLAUDE.md found): "Don't forget to say why. Code alone is not documentation. Use comments to explain why you wrote the code the way you did. Show your workings." "Comments are well-written prose describing the code, not just scribblings in the margin." — [TIGER_STYLE.md](https://github.com/tigerbeetle/tigerbeetle/blob/HEAD/docs/TIGER_STYLE.md)
- **Jon Gjengset's personal config** (dotfiles, not a project): "Apply literate programming principles to make code self-documenting and maintainable across all languages", with a limit: "Avoid over-documenting: Simple utility functions where intent is clear from the signature" — [jonhoo/configs](https://github.com/jonhoo/configs/blob/HEAD/agentic/.claude/CLAUDE.md)

#### Marker conventions and mechanical checks ([R])
- **telegramdesktop**, the most complete design found (1,013 lines, line 416, last commit 29 Oct 2026): "A comment is one line; two or three only when the block opens with `// WHY:`. A commit may add two comment lines plus one such exception, and a trailing comment is a line too; only `} // namespace X` closers and `#endif // X` labels are free. Say why, never what. Hooks enforce it, and `Telegram/SourceFiles/test/` is exempt." Also "**Never cite line numbers** in comments" because "Line numbers drift with every edit and nothing updates them." — [tdesktop AGENTS.md](https://github.com/telegramdesktop/tdesktop/blob/HEAD/AGENTS.md). I did not locate the hook source.
- **PostHog** tags rules by their enforcer: "`[lint: <id>]` means a linter, semgrep rule, or invariant test blocks it, so CI is the check and this text is only the reasoning. `[review]` means nothing catches it automatically — a reader is the only control." Its automation order: linters, then lint-staged or husky, then skills, then "AGENTS.md / CLAUDE.md instructions — when automated enforcement isn't suitable". All comment rules are tagged `[review]` — [posthog AGENTS.md](https://github.com/PostHog/posthog/blob/HEAD/AGENTS.md)
- **PostHog skill** gate: "**What does this tell a future reader that the code itself doesn't?**" It deletes "Perishable measurements and current-state stamps" but keeps "A dated snapshot: `# as of August 2024, Homebrew ships 4.13.2` (the date makes staleness visible)" — [writing-code-comments](https://github.com/PostHog/posthog/blob/HEAD/.agents/skills/writing-code-comments/SKILL.md)
- **Biome** routes to an on-demand skill: "Load doc-comments whenever editing `//`, `///`, or `//!` comments, including comments added incidentally." — [biome AGENTS.md](https://github.com/biomejs/biome/blob/HEAD/AGENTS.md)
- **`AIDEV-` anchors** (practitioner convention; small repos): julep-ai/steadytext uses "`AIDEV-ANCHOR:` (headings), `AIDEV-REF:` (cross-refs), `AIDEV-TODO:` (tasks), `AIDEV-NOTE:` (context), `AIDEV-QUESTION:`", "Ultra-short phrases (≤60 chars), no filler words", "Keep ~1 anchor per 40-60 lines", and forbids "Remove anchor comments without updating references accordingly" — [steadytext CLAUDE.md](https://github.com/julep-ai/steadytext/blob/HEAD/CLAUDE.md). market_prices says "'AIDEV-NOTE' - these comments are specifically addressed to you." — [market_prices AGENTS.md](https://github.com/maread99/market_prices/blob/HEAD/AGENTS.md)
- **uv**: "ALWAYS write `SAFETY` comments following our usual style when writing `unsafe` code" — [uv AGENTS.md](https://github.com/astral-sh/uv/blob/HEAD/AGENTS.md)
- **Spark** gives a grep to run: "scalastyle flags some of these. Spot-check before committing" for non-ASCII comment characters — [spark AGENTS.md](https://github.com/apache/spark/blob/HEAD/AGENTS.md)
- **Rust** prohibits comment authorship for upstream work: "Never generate or rewrite non-trivial PR descriptions, issue bodies, public comments, user-facing documentation, diagnostic messages, or source comments." "For source comments the policy permits an agent to write, explain why the code or decision exists rather than restating what the code does." — [rust AGENTS.md](https://github.com/rust-lang/rust/blob/HEAD/AGENTS.md)

#### Contradictions in real files
- **Inside one repo:** Turso's root file says "Where the code alone can't explain why something is done, a short plain comment is welcome." — [turso AGENTS.md](https://github.com/tursodatabase/turso/blob/HEAD/AGENTS.md). Its linked guide says "Do not add comments. Instead, focus on making your code expressive." — [code-quality.md](https://github.com/tursodatabase/turso/blob/HEAD/docs/agent-guides/code-quality.md). Anthropic warns such conflicts get resolved arbitrarily (first section).
- **Links:** Prisma says "Prefer links to canonical docs over long comments." Grafana says "Never include links (Slack, GitHub, Jira, etc.) in code comments."
- **References to issues:** dotnet avoids issue or PR numbers in regression comments, and Claude Code's prompt bans them. PostHog's skill instead keeps "a pointer to context a future reader can't reconstruct", while banning "per PR #1234".
- **Doc comments:** VS Code says "Use JSDoc style comments for `functions`, `interfaces`, `enums`, and `classes`" — [vscode copilot-instructions](https://github.com/microsoft/vscode/blob/HEAD/.github/copilot-instructions.md). Ruff, Prisma and Zed do not.

#### No comment content policy in sample ([R])
Files read that have no rule on comment content, or only on formatting, wording or public surfaces: [Anthropic's own claude-code](https://github.com/anthropics/claude-code/blob/HEAD/CLAUDE.md), [next.js](https://github.com/vercel/next.js/blob/HEAD/AGENTS.md), [react](https://github.com/facebook/react/blob/HEAD/CLAUDE.md), [cpython](https://github.com/python/cpython/blob/HEAD/AGENTS.md), [node](https://github.com/nodejs/node/blob/HEAD/AGENTS.md), [angular](https://github.com/angular/angular/blob/HEAD/AGENTS.md), [ghostty](https://github.com/ghostty-org/ghostty/blob/HEAD/AGENTS.md), [transformers](https://github.com/huggingface/transformers/blob/HEAD/AGENTS.md), [deno](https://github.com/denoland/deno/blob/HEAD/CLAUDE.md), [clickhouse](https://github.com/ClickHouse/ClickHouse/blob/HEAD/AGENTS.md).

### Inferences
- Rule position is not a settled practice: line 4 of 190 (Zed), 6 of 39 (Kubernetes), 77 of 251 (llama.cpp), 140 of 253 (Airflow), 205 of 239 (Bun), 222 of 362 (workerd), 234 of 239 (Ruff), 257 of 354 (PostHog), 416 of 1,013 (tdesktop). Many of these maintained files exceed Anthropic's 200-line target.
- The wording pattern that recurs in the more developed files: name the reader (no access to the PR or session), give a gate question, list what stays, list what goes, and show one GOOD and one BAD.
- Comment rules are becoming a response to agent habits. llama.cpp, Home Assistant and PostHog word them that way. None of the repos publishes before-and-after data on whether the rule worked.

### Gaps
- The 43-repo sample is my pick of well-known names, not random, so "21 of 43" is descriptive only. `openai/codex` root `AGENTS.md` returned 404. `duckdb` and `elasticsearch` `CLAUDE.md` came back empty.
- I found no well-known repo with a rule such as "comments must carry a source and measurement". Search coverage is limited to `gh search code` phrases and the sample, so absence is weak evidence.
- I did not read tdesktop's or any other repo's enforcement script, so how "hooks enforce it" works is unverified.

## What do empirical studies of agent context files find?

### Takeaway
Results conflict by outcome measured. On task success: Gloaguen finds LLM-generated files slightly hurt (-0.5% to -3%), developer-written help a little (+4%), and all raise cost (+19 to +23%). Guardrails finds any rules give +7 to +14 percentage points, random as much as curated. On efficiency: Lulla finds runtime -28.64% and output tokens -16.58% on small PRs with no correctness check. Compliance studies show agents follow files strongly but not reliably: 60 to 68% on a trivial marker. No study measures a comment rule except one nine-run blog test.

### Cited Findings

#### Effect on task success and cost ([M])
- **Gloaguen, Mündler, Müller, Raychev, Vechev**, arXiv:2602.11988, 12 Feb 2026. Design: SWE-bench Lite (300 tasks, 11 repos, LLM files only) and new AGENTbench (138 instances, 12 repos, developer files); Claude Code with Sonnet-4.5, Codex with GPT-5.2 and GPT-5.1 mini, Qwen Code. Abstract: "context files tend to reduce task success rates compared to providing no repository context, while also increasing inference cost by over 20%" and "unnecessary requirements from context files make tasks harder, and human-written context files should describe only minimal requirements." — [paper](https://arxiv.org/html/2602.11988v1)
  - LLM-generated: resolution -0.5% (SWE-bench Lite) and -2% (AGENTbench); steps +2.45 and +3.92; cost +20% and +23%. The introduction says "a decrease of 3% on average", which disagrees with the body's 2% on AGENTbench. — [paper](https://arxiv.org/html/2602.11988v1)
  - Developer-written: "an increase of 4% on average", better than no file "for all agents but Claude Code", steps +3.34, cost "at most 19%". — [paper](https://arxiv.org/html/2602.11988v1)
  - Reasoning tokens with LLM files: +22% GPT-5.2 and +14% GPT-5.1 mini on SWE-bench Lite; +14% and +10% on AGENTbench. Developer files: +20% and +2%. — [paper](https://arxiv.org/html/2602.11988v1)
  - Instructions are followed: "`uv` is used 1.6 times per instance on average when mentioned in the context files, compared to fewer than 0.01 times when it is not mentioned"; repo-specific tools 2.5 versus fewer than 0.05. "this result implies that the absence of improvements with context files is not due to a lack of instruction-following." — [paper](https://arxiv.org/html/2602.11988v1)
  - Files averaged 641.0 words (range 24 to 2,003) and 9.7 sections, per the summariser's read of the paper. Python only. Comments are not studied. — [paper](https://arxiv.org/html/2602.11988v1)
- **Lulla, Mohsenimofidi, Galster, Zhang, Baltes, Treude**, arXiv:2601.20404v2, 30 Mar 2026, JAWs 2026. Codex with gpt-5.2-codex, 10 repos, 124 small merged PRs (≤100 LoC, ≤5 files), paired with and without a root AGENTS.md. — [paper](https://arxiv.org/html/2601.20404v2)
  - Wall clock: median 98.57 s to 70.34 s (-28.64%), mean 162.94 s to 129.91 s (-20.27%). Output tokens: median 2,925 to 2,440 (-16.58%), mean -20.08%. Total tokens: median +1.29%, mean -9.93%. Only wall clock and output tokens are marked significant (Wilcoxon, p<0.05). — [paper](https://arxiv.org/html/2601.20404v2)
  - "Comparable task completion" rests only on a manual check of 50 sampled tasks. Correctness is out of scope. Repos were filtered to files containing conventions, structure and description. — [paper](https://arxiv.org/html/2601.20404v2)
- **"Guardrails Beat Guidance"**, arXiv:2604.11088v2, 28 May 2026 (first title "Do Agent Rules Shape or Distort?"). Claude Code with Opus 4.6, over 5,000 runs on SWE-bench Verified, 679 rule files (25,532 rules), 58 discriminative tasks. — [abstract](https://arxiv.org/abs/2604.11088)
  - "Random rules improve a coding agent's task performance as much as expert-curated ones (both +13.8pp ...)". All seven rule conditions beat no rules by 7 to 14 pp, random and curated both at 63.8%. "pass rates remain stable across rule counts from 0 to 50". — [paper](https://arxiv.org/html/2604.11088)
  - Polarity: on per-rule removal (n=35), the 3 helpful rules were all "do not" and the 4 harmful all "do". Fisher p=0.029. "do not refactor unrelated code" showed a 20 pp drop on removal (McNemar p=0.016). "Follow code style" was distorting (p=.180). 11 of 18 rules were inert. — [paper](https://arxiv.org/html/2604.11088)
  - Authors' own limits: "No individual McNemar comparison reaches p<0.05 at n=58; the headline rests on direction, not magnitude." The polarity rule rests on 7 rules, and the one significant comparison "would not survive a strict multiple-comparison correction". Outcome is bug-fix pass rate, not rule adherence. The word "comment" does not occur in the paper's HTML text. Code style is 6.5% of scraped rules. — [paper](https://arxiv.org/html/2604.11088)

#### Content and evolution of files ([M], descriptive)
- **Agent READMEs**, arXiv:2511.12884v2, 9 Aug 2026. 2,303 files, 1,925 repos. "complex, difficult-to-read artifacts that evolve like configuration code through frequent, small additions." Testing 75.9%, implementation details 70.8% (which includes code style), architecture 68.1%, security 14.8%, performance 14.5%. Median words: Copilot 535.0, Claude Code 485.0, Codex 335.5. No comment-specific result found. — [paper](https://arxiv.org/html/2511.12884)
- **dos Santos, Costa, Montandon, Silva, Valente**, "Configuration Smells", arXiv:2606.15828v5, SCAM 2026. 100 popular repos. Lint Leakage 62% (58 of 62 confirmed manually), Context Bloat 42% (threshold 200 lines; largest 1,477), Skill Leakage 35% (29 of 35 confirmed). Skill Leakage and Conflicting Instructions "increase the likelihood of Context Bloat by 83%". The smell catalogue comes from 14 grey-literature articles, and the 200-line threshold is taken from Anthropic's docs. It measures prevalence, not harm. — [paper](https://arxiv.org/html/2606.15828)
- **Mohsenimofidi et al.**, arXiv:2510.21413v4, 5 Feb 2026. 466 projects. "there is no established content structure yet", with variation in form: "descriptive, prescriptive, prohibitive, explanatory, conditional". It proposes studying co-evolution with code "similar to the co-evolution of source code and comments". — [abstract](https://arxiv.org/abs/2510.21413)
- Other surveys: 253 CLAUDE.md files in 242 repos, shallow hierarchy, commands and architecture dominate — [arXiv:2509.14744](https://arxiv.org/abs/2509.14744). 328 Claude Code config files, architecture emphasised — [arXiv:2511.09268](https://arxiv.org/abs/2511.09268). 401 repos of Cursor rules, whose code-style theme includes "commenting practices" — [arXiv:2512.18925](https://arxiv.org/html/2512.18925).

#### Result that files hurt, and the contradiction ([M])
- **Do context files help?** Lulla: faster, fewer output tokens, correctness unmeasured, Codex only. Gloaguen: cost up over 20%, LLM files lower success, human files marginally raise it and not for Claude Code. Guardrails: +7 to +14 pp on a selected subset, but content-independent. These measure different outcomes on different task sets and do not cancel.
- **Vendor advice versus Gloaguen:** the abstract says context files are "strongly encouraged by agent developers" and recommends the reverse for generated files: "omitting LLM-generated context files for the time being, contrary to agent developers' recommendations". — [paper](https://arxiv.org/html/2602.11988v1)
- **More content versus minimal content:** Gloaguen says minimal only. Guardrails finds no accumulated damage from 0 to 50 rules. Guardrails' measure is pass rate on 58 selected tasks, and it did not measure cost.

### Inferences
- A comment rule has no direct measured effect on task success. The relevant cost is one more instruction the agent must attend to, which Gloaguen's mechanism (more steps, more reasoning) suggests is small for one line but not zero for a long section.
- Context-file studies score bug fixing. Comment quality is a maintenance outcome that none of them measures, so "context files do not raise success" does not argue against a comment rule.

### Gaps
- No controlled study found on comment rules, comment quality or comment density as affected by context files. The comment density of agent-written code is not covered here.
- Gloaguen's iclr.cc listing was seen in search results only and the track was not verified — [iclr.cc listing](https://iclr.cc/virtual/2026/10021142).

## Does length, position, specificity or a mechanical check change how often an agent follows an instruction?

### Takeaway
Within 25 to 500 lines, the only large factorial study finds no detectable effect of file size or position, on Claude Code, with a trivial marker. That contradicts Anthropic's "reduce adherence" and the "put it at the top" advice. The big effects are elsewhere: session decay (first omission at a median of the fourth generated function), task type (26.2 pp), model (12.8 pp, and 0% versus 100% in one comment test) and rules that oppose defaults (3.6 to 7.4 points lower). No head-to-head of a hook or linter against prose was found. Its advantage is by construction for what it can check, and the "100% versus 70-90%" figure in circulation is unsourced.

### Cited Findings

#### File size and position ([M])
- **McMillan**, arXiv:2605.10039, 11 May 2026, single author. 1,650 Claude Code CLI sessions, 16,050 function observations, 2 TypeScript codebases, primarily Sonnet 4.6. The target is a marker statement, `// @tracked`, detected by AST; zero spontaneous emission across 1,669 baseline observations. — [abstract](https://arxiv.org/abs/2605.10039); [PDF](https://arxiv.org/pdf/2605.10039) (PDF text decoded by my own script from font maps; numbers below are from that text)
  - **Size** (25, 100, 250, 500 lines, target at line 2): compliance 60.0%, 65.2%, 67.7%, 64.0%. GLMM p=0.16. BF10 between 0.05 and 0.10 for the null. Power to detect a 10 pp shift on size is only 70%. — [PDF](https://arxiv.org/pdf/2605.10039)
  - **Position** (lines 2, 63, 128, 187, 250 of 250): 67.7%, 63.2%, 64.0%, 64.0%, 61.8%. GLMM p=0.83. No polynomial shape detectable. This null is a "failure to reject" without Bayes-factor support. Line 2 is the highest descriptively, 5.9 pp above line 250. — [PDF](https://arxiv.org/pdf/2605.10039)
  - **Splitting**: adding AGENTS.md and nested CLAUDE.md files around a target kept in the root CLAUDE.md shows no contrast. A contradictory AGENTS.md line shows none either. The author's bounds: "A 5,000-line CLAUDE.md exists in some large repositories and is well outside our design". — [PDF](https://arxiv.org/pdf/2605.10039)
  - **Session decay, the largest effect**: "approximately 5.6% lower odds of compliance per generation step (OR = 0.944)", non-monotonic, "median first omission at generation position 4". It was found post hoc but reproduces on a second codebase and on Opus 4.6. — [PDF](https://arxiv.org/pdf/2605.10039)
  - **Task**: a 26.2 pp gap between a refactor of an existing layout and a greenfield build, given as a single contrast and not a general rule. **Model**: Opus 4.6 at 54.9%, 12.8 pp below Sonnet 4.6 at the same config. — [PDF](https://arxiv.org/pdf/2605.10039)
  - **Author's advice**: "Focus on content rather than length within this range". "Layer in-session mechanisms (agent hooks that re-surface the rule, agent-managed memory) with post-hoc enforcement (linters, CI checks)". The study did not test hooks or linters, and it says "transfer of the absolute compliance rate to other instruction classes is an open question". — [PDF](https://arxiv.org/pdf/2605.10039)
- **IFScale**, Jaroslawicz et al., arXiv:2507.11538, [NeurIPS 2025 listing](https://neurips.cc/virtual/2025/122417). 10 to 500 keyword-inclusion instructions, 20 models. Best 68% at 500. Reasoning models gemini-2.5-pro and o3 stayed near-perfect "through 150 or more instructions". Others decay linearly (gpt-4.1, claude-3.7-sonnet) or exponentially (claude-3.5-haiku, llama-4-scout). Primacy peaks "around 150-200 instructions" and fades above 300: "while packing more important instructions towards the beginning of a prompt may help, it becomes a less effective strategy once extreme densities are reached." Writing task, older models, one-shot, not agents. — [paper](https://arxiv.org/html/2507.11538v1)
- **ClayBuddy**, arXiv:2606.19380v5, 26 Aug 2026. Long context, not long files: padding the transcript with CPython source "led to instruction following failure in 56/100 and 70/100 samples" on two tasks. Prohibited-file rules from a ~137,394 CLAUDE.md scrape: "Violations happened up to 19% of the time" when the violation made the task trivial. The authors state "we were unable to use the proprietary Claude Code, Codex, and Antigravity agent harnesses", so those harnesses' own mechanisms are not part of the result. — [paper](https://arxiv.org/html/2606.19380)

#### Opposing defaults, conflict and staleness ([M])
- **Harness-IF**, arXiv:2608.11727, 12 Aug 2026. 60 multi-turn items from a 642-rule library, 256 rules with verdicts, 5 configurable surfaces, 12 frontier models. "accuracy spans 72.1-85.9% and AP-Acc 66.1-78.6%; every model is worse on against-prior rules, by 3.6 to 7.4 points (mean 5.81)". "pooled precedence does not follow prompt depth, with system prompts, project files, and user instructions ahead of tool and skill descriptions." — [abstract](https://arxiv.org/abs/2608.11727). Abstract only: no HTML, and I could not decode the PDF.
- **Stale Instruction Files**, arXiv:2610.30571, 22 Oct 2026. 40 small synthetic Python projects, 320 runs, Claude Code 2.1.302 with Claude Sonnet 5.5 and Codex CLI 0.163.0 with GPT-6 Sol. "90.1% of the agents' choices followed the stale file." "Claude Code pointed out the conflict in 79 of 80 runs and still followed the file." "Codex CLI rewrote the existing code to match the file in 20 of 80 runs, and the project's own tests then failed in 17 of them." One sentence moved choices that follow the code from 4.2% to 91.4% and tests from 89.4% to 100%. The authors attribute this to the file reaching the model as an instruction and the code as tool output. — [abstract](https://arxiv.org/abs/2610.30571); [paper](https://arxiv.org/html/2610.30571)
  - The sentence: "When a repository's documentation and its existing code disagree, follow the conventions used in the existing code, and in your final reply point out each inconsistency you found between the documentation and the code." — [paper](https://arxiv.org/html/2610.30571)
- **Only direct comment-format datum, informal**: Umans blog. One real repo, nine configurations, one run each, rule to write Given/When/Then test comments. Gemini 3 Pro 0% in both Gemini CLI and Cursor. Opus 4.5 98%. The other six configurations 100%. — [Umans blog](https://blog.umans.ai/blog/agent-apply/)

#### Specificity and wording
- [V] Specificity improves following: Anthropic, Factory ("Avoid vague rules that cannot be checked"), Windsurf, Cursor, GitHub (first section). I found no controlled measurement of specificity on rule adherence in coding agents.
- [M] Polarity: "constrain what agents must not do, rather than prescribing what they should." Scored on pass rate, thin at rule level. — [Guardrails](https://arxiv.org/abs/2604.11088)
- [V, no data] Emphasis: Anthropic says it mostly causes over-application. [R] Practice is mixed: uv uses ALWAYS and PREFER, Bun uses **CRITICAL**. I found no measurement.
- [R, untested] Examples: llama.cpp, Turso and PostHog use GOOD and BAD samples. [O] GitHub's blog: "One real code snippet ... beats three paragraphs". No measurement found.

#### Mechanical checks
- [V] Hooks are deterministic for what they can detect, and hook output returns to Claude: "A `PostToolUse` hook that runs your linter feeds results back as text Claude reads" — [features overview](https://code.claude.com/docs/en/features-overview)
- [V, caution] Anthropic warns against turning preferences into hooks: "`Prefer named exports` has plenty [of exceptions], so that one stays in `CLAUDE.md`." "Most of the time, you want Claude to decide." — [best practices](https://code.claude.com/docs/en/best-practices)
- [O] Unsourced claim: "prompt-based instructions achieve 70-90% compliance, while hooks reach 100%", as summarised by search and with no study behind it. Do not use it as data — [dotzlaw](https://dotzlaw.com/insights/claude-hooks/)
- [M, descriptive] Lint Leakage in 62% of files. The critique is that context is spent on checkable rules. It does not measure compliance. — [dos Santos](https://arxiv.org/html/2606.15828)
- [M, partial] ClayBuddy's harness modification: "it eliminates violations across some tasks", on safety rules and a custom harness. — [ClayBuddy](https://arxiv.org/abs/2606.19380)

#### Contradictions between advice and measurements
1. **Length.** Anthropic: "Longer files consume more context and reduce adherence" — [memory](https://code.claude.com/docs/en/memory). McMillan, on Claude Code itself: no size effect from 25 to 500 lines, with affirmative-null Bayes factors — [PDF](https://arxiv.org/pdf/2605.10039). Partial reconciliation: Gloaguen's cost effect and IFScale's decay above 150 instructions are real at other scales or for other outcomes, and McMillan's marker has no comprehension load.
2. **Position.** Factory ("Keep the top of each file dense") and GitHub ("early section"), plus IFScale's primacy, against McMillan's position null (p=0.83). McMillan's null is weak: no Bayes-factor support, and a 5.9 pp descriptive gap would go undetected.
3. **Splitting files.** Anthropic recommends path-scoped rules for adherence, and McMillan says "the architecture-null result does not support" multi-file configuration as a remedy. McMillan always kept the target in the root file, so this is not a test of scoping the rule itself; adherence from path-scoped loading remains unmeasured.
4. **"Agents follow rules."** Gloaguen ("generally follow"), Stale Files (90.1%) against McMillan (60 to 68% on a trivial marker), Harness-IF (72.1 to 85.9%), ClayBuddy (up to 19% violations under temptation). The difference is what is scored: a task-relevant tool or a one-off choice is followed easily, and a per-function repeated duty decays.
5. **Positive wording.** Anthropic's model example is positive ("Use 2-space indentation"). Guardrails finds positive directives distorting and negative constraints beneficial, on thin rule-level data and a different outcome.
6. **Conflicting files.** Anthropic: "Claude may pick one arbitrarily". McMillan: a contradictory instruction in an adjacent AGENTS.md shows no penalty. Harness-IF: precedence depends on surface, skills ranking low. Stale Files: the file beats the code. These are different conflict types.
7. **Compaction.** llama.cpp tells agents the comment rule "often gets lost between context compactions", while Anthropic says the root CLAUDE.md is re-injected after `/compact`. Neither is measured; llama.cpp's note is not specific to one agent, and McMillan's decay shows loss without any compaction claim.

### Inferences
Wording, all inference from the above; no study tests a comment rule, and these should be measured in the repo.
- **State the policy as what stays and what goes, with a named reader.** The convergent form in Airflow, uv, Biome and Ruff, tied to a reader "with no access to the session".
- **Say what it overrides, if it departs from defaults.** A rule that keeps long or sourced comments opposes Claude Code's and Codex's defaults, which Harness-IF marks as the weak class. Wording such as "this overrides any default to write few comments" states the precedence explicitly. The Stale Files result shows one precedence sentence can move behaviour from 4.2% to 91.4%, though on convention choice and not comments.
- **Pair the positive duty with hard negatives.** "Never narrate the next line, the session or the diff" and "do not delete or shorten an existing comment unless it is false". Guardrails favours negatives, and Stale Files shows Codex can rewrite existing code to match a new rule (20 of 80 runs), so a guard against mass rewriting of existing comments is justified. Elasticsearch, Ruff, PostHog and tdesktop all carry one.
- **Avoid adding emphasis** beyond plain wording, per Anthropic. No data either way.
- **Give one GOOD and one BAD from the repo.** Practice in llama.cpp, Turso and PostHog; not measured.
- **Avoid a sibling rule that contradicts it.** Turso shows how this happens through a linked guide.

Placement.
- **In a very long file, position alone is not worth a fight.** McMillan finds no detectable effect in 250 lines. Top placement costs nothing and is the descriptive best (67.7% at line 2 versus 61.8% at line 250), so it is a cheap hedge, not a remedy. In a file with a stable schema, following the schema (one named rule in the existing rule list) seems better than breaking it.
- **Size of the file in question:** [AGENTS.md](/Users/max/ws/chesso/AGENTS.md) is 323 lines and 19,570 bytes, its `## Project rules` starts at line 107, and [CLAUDE.md](/Users/max/ws/chesso/CLAUDE.md) adds 246 lines and imports AGENTS.md first. Combined 569 lines is just above McMillan's tested range and nearly three times Anthropic's target.
- **Keep one short rule in the always-loaded file**, and move long guidance and examples to an on-demand skill or linked file. PostHog and Biome do this. Caveat: Harness-IF ranks skill descriptions low in precedence, and McMillan's session decay concerns attention rather than presence, so the one-line rule must stay in the main file.
- **Claude-only rationale** can sit in a block-level HTML comment at zero context cost (first section; behaviour through `@` imports unverified).
- **Avoid a nested `src/AGENTS.md` for Claude Code** in a repo with a root `CLAUDE.md`, and check how `.claude/rules/` paths interact with other agents, since those files are Claude-specific.
- **Subagents:** "The built-in Explore and Plan agents start with neither" CLAUDE.md nor git status, and an agent definition with `omitClaudeMd` skips the files — [features overview](https://code.claude.com/docs/en/features-overview). A workflow where subagents write the code should confirm they load the rule or carry it in the brief.

Enforcement.
- **Split the rule into what a script can see and what it cannot.** A script can check a comment-line budget (tdesktop), a marker such as `// WHY:`, forbidden tokens (line numbers, PR numbers, "previously", "AI:"), and ASCII. It cannot check "why, not what". PostHog's `[review]` tag admits this openly.
- **Run the checkable part at the diff or commit gate**, and treat the rest as review. For the judgment part, the options are a fast-check reviewer, or Anthropic's comment-analyzer pattern, noting that a `prompt` or `agent` hook "asks *another model* to decide, so it isn't deterministic either" per [best practices](https://code.claude.com/docs/en/best-practices).
- **Re-surface at edit time for long tasks.** McMillan's decay (first omission around the fourth function) suggests that a re-surfacing mechanism during edits is where the leverage lies, and a post-edit check that prints the rule only when a comment was added costs context only when it fires. Untested.
- **Measure compliance in the repo** against a baseline, since the published numbers come from a single trivial marker. McMillan's AST method (count per function) transfers to any mechanically checkable part of the rule.

### Gaps
- No head-to-head of hook or linter against prose for a coding-style rule, with rates, was found. Claims of 100% are by construction or unsourced.
- No measurement of specificity, emphasis, examples or rule length on compliance in coding agents.
- No compliance data on long files above 500 lines, on C++ or other non-TypeScript codebases (McMillan), or on models later than Opus 4.7 for size and position. Stale Files used newer models but a different question.
- McMillan and Harness-IF are recent preprints. I found no evidence of peer review, and I read Harness-IF only as an abstract.
- Comment rules specifically: only the nine-run Umans test (format compliance), and no data on quality or on rules asking for longer comments.
