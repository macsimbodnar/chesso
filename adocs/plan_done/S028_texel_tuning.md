## Why this runs first

It was 28th in the plan and it is now next. DEC-033 measured what kind of defect
gives the centipawns away: 160 expensive moves re-asked at sixteen times the
search removed 24.1 % of the error and left 95 of 160 moves unchanged. The engine
mostly believes the move it played. What it believes it with is material plus a
piece-square table written by hand, which `eval_tables.hpp` itself calls a
starting point and nothing more.

Nothing else on the plan touches that. The search block is bounded at about
10 cp per effective doubling on the same population, and every S027 term added
before the tuner exists is measured against unfitted tables, so a term that
measures zero cannot be told from a term whose weight is wrong.

## Needs

A few hundred thousand quiet positions with known game outcomes, generated by
self-play, and a tuner. Worth more than several S027 terms put together: it is
what turns a set of plausible numbers into a tuned evaluation. Hand-picked
weights are the wrong weights, including the ones written by hand in S010 --
which are hand-written precisely because the published tuned ones were refused
(DEC-016).

## Split of work

The agent builds the tuner, generates and prepares the self-play data, and
states exactly what the run should be: inputs, objective, hyperparameters,
expected duration. **The owner executes the fit.** The constants come back and
are then measured by SPRT like any other change. DEC-015.

## What was built

| file | what |
|---|---|
| `tools/datagen.cpp` | self-play position generator. Writes `fen result score phase`; quiet positions only |
| `tools/eval_model.hpp` | `evaluate()` as a linear function of its own 773 constants. Shared by the tuner and by the test that keeps it honest |
| `tools/tuner.cpp` | the Texel fit: Adam on full-batch gradients, held-out validation, writes a pasteable header |
| `tests/test_eval_model.cpp` | the model computes what `evaluate()` computes, on 13 positions from a full board to bare kings |

The model is the load-bearing piece. The tuner never calls the search or
`evaluate()`; it fits a floating-point rewrite of them, because a fit needs a
derivative and because a pass over a million positions has to cost milliseconds.
A model that drifts from the engine would fit the wrong function and produce
constants that look tuned and are not, and nothing downstream would notice. The
test was observed red: dropping the black mirror in `parse_placement` puts 408
centipawns of disagreement on the start position.

Two things were found while building it and neither is an engine defect. A
`game_t` that never sees `initialize_game_const_data()` has all-zero zobrist
keys, so every position hashes to zero, the transposition table collapses onto
one entry and repetition detection calls a draw two plies into every game. It
cost an hour and produced a dataset of 37 positions. The other is that the
tuner's parameterisation is degenerate by five dimensions -- adding c to every
square of `psqt_mg[t]` and `psqt_eg[t]` is the same evaluation as adding c to
`piece_value[t]` -- which is harmless and is stated in the file so nobody reads
meaning into the reported piece values.

## The run, for the owner to execute

**Data.** Generated by the agent, in `.tuning/selfplay_v1.tsv`, gitignored:

```bash
build/tools/datagen --out .tuning/selfplay_v1.tsv \
    --games 20000 --nodes 100000 --threads 3 --seed 20260810
```

20000 self-play games, 100000 nodes per move, 8 uniform random opening plies,
openings discarded past 400 cp, adjudicated at 2000 cp held for 6 plies, quiet
positions only. About 77 positions a game, so roughly 1.5 M rows, about 95
minutes on three threads.

**Fit.** This is the part the agent does not run:

```bash
build/tools/tuner --data .tuning/selfplay_v1.tsv \
    --out .tuning/tuned_tables.hpp --threads 3
```

| | |
|---|---|
| objective | mean squared error of `sigmoid(K * evaluate())` against the game result |
| parameters | 773: `piece_value[0..4]`, `psqt_mg[6][64]`, `psqt_eg[6][64]` |
| start | the constants the engine ships, so the reported starting error is theirs |
| K | fitted from the data on the starting constants, then held |
| optimiser | Adam, `--lr 1.0`, `--epochs 20000` |
| validation | 10 % held out, shuffled first because a game's positions are consecutive and share a label |
| stopping | best held-out error kept; stops after `--patience 20` reports without improvement |
| expected duration | full-batch, three threads: seconds per epoch at 1.5 M rows |

What to check when it finishes: held-out error must be below the starting
figure, and the tuner prints a warning and refuses to claim otherwise if it is
not. Then paste `.tuning/tuned_tables.hpp` over the corresponding definitions in
`src/eval_tables.hpp` and run `./fastchess.sh --fast`. Nothing is kept without
that verdict, and a verdict of zero is recorded as zero.

**Disclosure.** The agent ran the tuner once, for 300 epochs on a 15406-position
smoke dataset, to show the program descends rather than to produce constants:
held-out error 0.117789 to 0.073804. That is the step's "reduces prediction
error on a held-out set" and nothing from it goes near `eval_tables.hpp`. If
even that crosses the DEC-015 line, say so and it will be recorded as a
correction.

## What actually happened

The owner delegated the fit for this one run (DEC-034) rather than typing the
command themselves, and it ran exactly as stated above: 1490839 positions,
1341756 train and 149083 held out, K = 1.1141 fitted from the data and then
held, Adam at lr 1.0, stopped at epoch 11200 when 20 consecutive reports failed
to beat the best. Held-out error 0.113852 to 0.108043, train 0.113554 to
0.107749. No refusal warning.

**Verdict: +188.74 +/- 32.21 Elo**, 438 games at 10+0.2, LLR 2.95 against a
bound of 2.94, H1 accepted. 294 wins, 77 losses, 67 draws, Ptnml [5, 9, 65, 44,
96]. Candidate `c31b995` against reference `9fc6fdf`. It is the largest single
change the project has measured, and it was 28th in the plan until DEC-033
moved it to the front.

### Three things went wrong on the way in

**The gate was already red.** `ae814b6` committed the four new files without
running `./clang-format.sh`, so every commit from there on failed the section 5
gate. Formatting only, `e0c338e`, found while establishing a baseline and fixed
before the measurement rather than after it.

**The paste did not compile.** `evaluation.cpp` defines `PAWN` to `QUEEN` after
including `eval_tables.hpp`, which defines the same five names. That only ever
worked because both sides held the same numbers; the fitted values turn it into
five `-Wmacro-redefined` errors under `-Werror`. The fix is not to unify them.
Move ordering needs a stable ranking, not an accurate price, and the `ORDER_`
bands clear each other by exactly 100 points, so a queen at 1026 in that
arithmetic is the silent strength regression `CLAUDE.md` warns about. The
ordering values keep their old numbers under `MVV_` names, `9fc6fdf`, shown
behaviour-neutral by identical node counts and best moves (INV-6).

**Nine anchor assertions moved**, which is what they are for. Every replacement
value was recomputed by a second implementation of `evaluate()` written over
the fitted constants, and the two agree exactly -- including `-474`, which is a
quiescence result and turns out to be the best of four king evasions. An anchor
copied from the thing it anchors asserts nothing.

### One test was wrong rather than stale

"promote to a queen" stood on `8/P6k/8/8/8/8/8/4K3`, where Stockfish at depth 20
finds **four** moves that all mate in ten. It asserted a preference among equals
and passed only because promotions are ordered first; the fitted endgame king
table, which likes the white king off e1, reordered them and it failed at depth
5. The black king moves to c7, where `a8=Q` is mate in 14 and the next best move
is +387. The new position passes on the hand-written tables too, so it tests the
engine and not the tuning. This is the third case in that file to have been
written this way, after two the file already documents.

### What this does not settle

The fit is over the constants that exist. `eval_tables.hpp` has two tables and
five values and nothing else, so a term chesso does not have cannot be fitted --
that is S027, and it now has a tuner to be fitted by. The 5.1 % of held-out
error the fit removed is not directly comparable to 188 Elo and nobody should
try: the objective is a prediction of game outcome, not a strength model.

The data is one generation of self-play at 100000 nodes a move. Nothing here
says a second generation, sampled from the stronger engine this produced, would
not do better; nothing here says it would either.
